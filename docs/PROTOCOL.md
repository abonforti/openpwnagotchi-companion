# WebSocket protocol

The **authoritative definition of every message shape is `docs/schemas/`** (JSON Schema
draft 2020-12), per SPEC.md D15. This document does not restate field lists — it would drift.
It describes the things a schema cannot express: framing, ordering, lifecycle, and the rules
both sides must obey.

- `docs/schemas/common.json` — shared shapes (`AccessPoint`, `Peer`, `Gps`, `Stats`, …).
- `docs/schemas/incoming/<type>.json` — one file per client → plugin message.
- `docs/schemas/outgoing/<type>.json` — one file per plugin → client message.
- `frontend/src/lib/protocol.ts` — TypeScript types generated from the above by
  `tools/gen-protocol-types.mjs`. Generated, committed, never hand-edited; CI fails if it is
  out of sync.

Adding or changing a message means editing the schema first, regenerating the types, and
updating the conformance tests. There is no other order.

## Transport

- WSS only, on `ws_port` (default 8082), bound to the IPv4 address of a configured tether
  interface. Never `0.0.0.0`.
- The PWA is served over HTTPS on `http_port` (default 8443) from the same certificate. An
  HTTPS page may only open `wss://`, never `ws://`; there is no plaintext fallback on either
  port, by design.
- One TLS certificate covers both ports and must carry an `iPAddress` SAN for every IP in use.
- Text frames carrying UTF-8 JSON. One JSON object per frame. No fragmentation of a logical
  message across frames, no batching of several messages into one.

## Framing

**Incoming messages are flat**: the payload fields sit next to `type`.

```json
{"type": "set_mode", "mode": "manual", "message_id": "c7f1"}
```

**Outgoing messages use an envelope**: the payload always lives under `data`.

```json
{"type": "acknowledgment", "data": {"acknowledged": "set_mode"},
 "timestamp": 1755264000.123, "message_id": "c7f1"}
```

This asymmetry is deliberate and locked: it matches the upstream `pwnios` client wire format
that the plugin was forked from, so an existing client keeps working.

- `timestamp` is epoch seconds as a float, set by the plugin at send time. It is required on
  every outgoing message.
- `message_id` is generated by the client, is opaque to the plugin, and is echoed back on both
  the `acknowledgment` and the substantive reply. A client that does not need correlation may
  omit it entirely.
- Unknown keys are rejected: every schema sets `additionalProperties: false`. A client that
  sends an extra field gets an `error` with code `bad_request`.

## Connection lifecycle

1. TLS handshake. A client that does not trust the private CA fails here, silently as far as
   the plugin is concerned.
2. If the plugin is configured with a non-empty `token`, the client's **first** frame must be
   `auth`. Anything else, or nothing at all within `auth_timeout` seconds (default 10), closes
   the connection with code `1008`. When no token is configured this step is skipped entirely.
3. **After** authentication has passed, never before it, the plugin sends an initial `stats`,
   `access_points` and `face_status` so the UI has state without asking. The ordering is a
   security requirement rather than a convenience: the burst carries the unit's state, and an
   unauthenticated socket must not receive it. The same gate admits the socket to the broadcast
   set, so an unauthenticated client receives no later push either — not the burst, and not
   `wifi_update`, `handshake`, `peer_detected` or `status_change`.
4. Steady state: the client polls what it needs and receives pushes as they happen.
5. `stats` arrives periodically, on the `keepalive_interval` tick, so an idle client can tell a
   quiet plugin from a dead link **and** can tell fresh data from stale. A frame that carries
   nothing proves only the first, and the client needs both. An empty `keepalive` goes out on
   the same tick and is kept for any client that already acts on it.

   **Decided, not yet shipped.** Today only the empty `keepalive` goes out. Issue #65 tracks it,
   and blocks on a real problem rather than on effort: the broadcast currently shares a thread
   with a blocking bettercap call, so its cadence is not something the plugin can promise from
   where it stands. Do not write a client that depends on the period until that is settled.
6. The client also sends `ping` on its own schedule and forces a reconnect if no `pong` comes
   back within its timeout. That direction matters separately: the periodic broadcast proves the
   downlink, and a command needs the uplink.

## Requests and replies

Every request in `docs/schemas/incoming/` that has a reply gets exactly one, carrying the same
`message_id`. When the request also carried a `message_id`, an `acknowledgment` is sent first.

**`acknowledgment` means accepted, not applied.** Two cases where the distinction matters:

- `set_pasv` emits `plugins.on('pasv_on'|'pasv_off')`, which pwnagotchi dispatches
  asynchronously onto each plugin's own thread. The new state is only observable in a later
  `stats`. The client shows the toggle as pending until `stats.mode` confirms it.
- `set_mode`, `reboot` and `shutdown` take effect by restarting or powering off the device.
  See below.

Failures reply with `error`. An `error` never closes the connection except for code
`unauthorized`.

## Disruptive commands

`set_mode`, `reboot` and `shutdown` all destroy the connection as a normal part of doing their
job. Switching between AUTO and MANU is **not** an attribute write — the mode is fixed at
process start, so changing it means `pwnagotchi.restart()`, which restarts both the `bettercap`
and `pwnagotchi` services and takes this plugin with them.

The sequence is always:

1. `acknowledgment` (when a `message_id` was supplied),
2. broadcast `restarting` to **every** connected client with the reason and, for a mode change,
   the target mode,
3. flush,
4. perform the action on a separate thread.

A client receiving `restarting` must treat the disconnect that follows as expected: display the
reason, suppress the error banner, and reconnect with backoff. Typical return time for a mode
change or reboot is 20-60 seconds; after `shutdown` there is nothing to reconnect to.

All three are gated behind a two-step confirm in the UI. That gate is a client-side affordance
only — the plugin executes as soon as the command arrives and does not expect a second frame.

## Pushes

These arrive unsolicited, driven by pwnagotchi hooks: `handshake`, `peer_detected`,
`wifi_update`, `channel_hop`, `status_change`, `face_status`, `gps_update`, `stats`,
`restarting`, `keepalive`.

- `face_status` is pushed only when the face or status text actually changed. The face is
  unicode text; no image is ever transported for it.
- `screen_image` is **never** pushed. The full e-ink PNG is on demand only — a Bluetooth PAN
  link cannot carry it continuously. A client wanting a live mirror polls `get_screen`, by
  default no faster than every 5 seconds.
- `wifi_update` and `access_points` carry the same mapping; the first is a push, the second a
  reply.

## GPS

`Gps` is a single uniform shape. There is no separate "disabled" form: when nothing is
available, `enabled` is `false` and every coordinate field is `null`.

`source` is one of `bettercap`, `gpsd`, `browser`, or `null`. Resolution priority is
bettercap → gpsd → browser → none, subject to the `gps_source` config.

`piFix` is `true` when an on-Pi source currently has a fix. **While `piFix` is true the client
must not send `gps_data`** — the browser reading is the worst of the three and must never
overwrite a device fix. Browser readings expire after 10 seconds.

Handshake GPS sidecars on disk use bettercap's own shape with capitalised keys
(`Latitude`, `Longitude`, …), so the stock `gps.py` plugin and `webgpsmap` keep working. The
`HandshakeGps` wire shape is the normalised read of that file and is never what gets written.

## Errors

`error.code` is a closed enum (`common.json#/$defs/ErrorCode`); clients switch on the code and
use `message` for display only. Codes worth handling explicitly:

| code | meaning |
|---|---|
| `unauthorized` | token missing, wrong, or the auth deadline passed. The connection closes. |
| `pasv_unavailable` | the `pasv_mode` plugin is not installed. Hide the control. |
| `pasv_requires_auto` | PASV is only meaningful while in AUTO. |
| `no_frame` | the e-ink frame file does not exist yet. Retry later. |
| `log_unavailable` | the configured log path could not be read. |
| `unknown_command` | the client sent a `type` this plugin version does not implement. |

`capabilities.pluginVersion` in `stats` lets a client detect a plugin older than itself and
disable features rather than firing commands that will come back `unknown_command`.

## Sizing

The link is Bluetooth PAN. Keep payloads small:

- `handshakes_list` is capped at 500 entries with `truncated: true` rather than silent loss.
- `log_lines` defaults to 200 lines and is capped at 1000, tailed from the end of the file.
- `screen_image` is base64 PNG, on demand only.
- Faces are text.
